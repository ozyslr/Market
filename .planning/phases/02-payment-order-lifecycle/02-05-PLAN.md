## Key Existing Code

### iyzico Refund API (from Plan 01 iyzico.cjs)
- `refundV2Create(client, { paymentTransactionId, price?, currency? })` — per-transaction refund for marketplace payments.
- `cancelCreate(client, { paymentId, ... })` — full payment cancel (use only for pre-shipment cancellations).

### Transaction Engine States
- `transitionEngine.ts`: Refund path: `return_requested -> approve_return -> return_approved -> refund -> refunded`.
- `SubOrder` stores `paymentTransactionId` (set in Plan 02 callback handler).

### Ledger (Phase 1 + Plan 04)
- Ledger entries have `type: 'order_charge' | 'commission' | 'payout' | 'refund' | 'adjustment'`.
- Plan 04 added `status` field: `'pending' | 'collected' | 'released' | 'reversed'`.
- Commission entries need `status: 'reversed'` on full refund (D-06: negative entry).

### Transition Flow for Refunds
- From the TRANSITION_MATRIX: `delivered -> request_return -> approve_return -> return_approved -> refund -> refunded`.
- The admin refund endpoint should handle the `refund` event on a SubOrder in 'return_approved' status.

### Existing Refund Routes
- `POST /api/refund` exists in `server/routes/stripe.ts` for Stripe refunds. Iyzico refunds need a separate endpoint due to different SDK calls.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Admin -> API refund endpoint | Admin authenticated; refund amounts calculated server-side |
| Server -> iyzico refundV2 API | paymentTransactionId sent for per-item refund; iyzico handles PCI-DSS |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-018 | Elevation of Privilege | POST /api/admin/refund | mitigate | verifyAdmin middleware; only admin role can process refunds |
| T-02-019 | Tampering | Refund amount manipulation | mitigate | Refund amount calculated server-side from original ledger entries; client cannot specify amount (per D-06) |
| T-02-020 | Spooldfing | iyzico refundV2 call | mitigate | paymentTransactionId sourced from SubOrder document (validated by Firestore read), not client input |
| T-02-021 | Repudiation | Refund audit trail | mitigate | Every refund recorded as immutable ledger entry with type 'refund', amount, hash chain linkage |
| T-02-022 | Tampering | Double refund | mitigate | Atomic transaction: ledger entries + status update in same Firestore transaction; SubOrder refunded status prevents second refund |
| T-02-SC | Tampering | Firebase deploy | accept | firebase deploy --only firestore:rules is a one-time blocking operation; no npm packages installed |
</threat_model>
