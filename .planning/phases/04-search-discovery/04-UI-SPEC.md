# Phase 4 — UI Design Contract: Search & Discovery

> Visual and interaction contract for Phase 4. This phase swaps the search ENGINE
> (Firestore/MOCK → Typesense) behind the EXISTING search UI. The contract documents
> the existing visual system so it stays consistent, and specifies net-new interaction
> states only. Do NOT redesign existing surfaces.
>
> Generated by gsd-ui-researcher. Verified by gsd-ui-checker.

## Net-New Interaction States (Phase 4 changes)

These are the only new or changed UI behaviors introduced by the Typesense engine swap.

### 1. Sort control — "best-selling" option

The existing `SORT_OPTIONS` array in `FilterPanel.tsx` does not include a "best-selling" sort. Add one entry:

```ts
{ value: 'best-selling', label: 'En Çok Satan' }  // TR
// EN: 'Best Selling' | DE: 'Meistverkauft' | AR: 'الأكثر مبيعاً'
```

Position: after "En Yeniler", before price options. Final order:

1. En Yeniler (newest — default, value `''`)
2. En Çok Satan (best-selling, value `'best-selling'`)
3. Fiyat: Düşükten Yükseğe (`price-asc`)
4. Fiyat: Yüksekten Düşüğe (`price-desc`)
5. En Çok Puanlanan (`rating`)

No visual change to the sort select dropdown — only add the option.

### 2. Facet counts from Typesense

`FilterPanel` already renders `({item.count})` beside each brand. When Typesense returns facet counts, they flow through the existing `FacetCounts` interface unchanged. No new UI.

Behavior: counts update on each query. Count `0` is NOT rendered (existing logic: `{item.count > 0 && ...}`). Keep as-is.

### 3. Typo-tolerant query echo (SRC-01)

When Typesense returns results for a corrected query (e.g., user typed "telofon", matched "telefon"):

- **Do NOT add a "Did you mean" UI element.** Typesense returns results anyway (typo tolerance). The existing results count heading already shows the query term. No extra surface needed.
- The `normalizeTR` function in `SearchResults.tsx` is removed from the Typesense search path (D-09) — this is a backend/service change only, no UI change.

### 4. Loading / skeleton state

- Existing: `SearchResultsSkeleton` component renders when `searchLoading === true`.
- Phase 4 change: Typesense queries are faster than the current 300ms artificial delay. Keep the skeleton but reduce or remove the artificial `setTimeout`. No visual change to the skeleton itself.
- Minimum display time: 150ms (prevents skeleton flash on fast responses). Implementation detail for executor.

### 5. Empty / no-results state

The existing empty state is already built (centered layout with bouncing `SearchIcon`). Lock the copy contract:

| Language | Heading                            | Body                                                                                              |
| -------- | ---------------------------------- | ------------------------------------------------------------------------------------------------- |
| TR       | "Global arşivler sessiz."          | "Sorgunuzla eşleşen ürün bulunamadı. Daha geniş kategorileri deneyin veya filtreleri temizleyin." |
| EN       | "The global archives are silent."  | "No artifacts matched your query. Try broader categories or clear your filters."                  |
| DE       | "Die globalen Archive sind still." | "Keine Artikel gefunden. Versuche breitere Kategorien oder lösche deine Filter."                  |
| AR       | "الأرشيف العالمي صامت."            | "لم يُعثر على نتائج مطابقة. جرّب فئات أوسع أو امسح مرشحاتك."                                      |

The "Use the AI Assistant" suggestion in the existing EN copy may be kept or removed — at executor's discretion (it references a deferred feature).

### 6. Typesense error / fallback state

When Typesense is unreachable and the fallback chain activates (D-07):

- No user-facing error message is shown. Results degrade silently to Firestore/MOCK data.
- If Typesense AND Firestore both fail (empty results from all sources): the existing empty state renders as normal.
- Do NOT add a "Search is degraded" banner — this would reveal internal architecture.

## RTL Support (Arabic — AR locale)

The existing layout already uses Tailwind logical properties throughout:

- `end-0`, `end-3`, `inset-y-0 end-0` — filter drawer slides from the correct edge in RTL
- `ps-*`, `pe-*` classes where present

**Phase 4 must maintain these conventions.** Specific requirements:

| Surface                         | RTL requirement                                                                                           |
| ------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Filter drawer                   | Already uses `end-0` — do not change to `right-0`                                                         |
| Active filter chip X icon       | Stays on the right in LTR, left in RTL — already handled by flex logical order                            |
| ArrowUpDown icon in sort select | Uses `end-3` — RTL-safe, do not change                                                                    |
| ChevronDown/Up in brand list    | Inline icon — no directional concern                                                                      |
| Breadcrumb separator `/`        | Replace with `\` for RTL display via CSS `[dir=rtl]` or keep `/` (both acceptable — confirm with product) |
| Arabic copy in empty state      | Provided above — use i18n key `search.emptyHeading` / `search.emptyBody`                                  |

No new RTL-specific CSS is required if logical properties are maintained.
